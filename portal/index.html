The problem

In a sandwich attack an adversary buys a token just before a user's swap (front-run), so the user trades at a worse price, and sells just after (back-run), keeping the difference. Existing tools mostly observe and report these attacks. They leave no persistent, verifiable consequence for the attacker.

Design

Architecture

Two detectors feed one confirmation stage. A confirmed attacker is written to a contract on Base Sepolia and shown on a dashboard.

Design goals

  1. Block-time operation. A block is analysed well inside the 12 s interval.
  2. Public data only. Only what a standard RPC provider exposes. No builder or relay access.
  3. Layered confidence. A cheap structural rule proposes, a stricter receipt check confirms.
  4. Auditable output. Each detection carries the three transaction hashes of the sandwich.
  5. On-chain consequence. A confirmed detection changes contract state.

Design

Layer 1: mempool detector

Screens pending transactions as they arrive. It is the only path that can report an attack before it is mined, but it sees a small part of the pool and found nothing on mainnet.

Pipeline

  1. Subscribe. eth_subscribe newPendingTransactions delivers hashes. Each connection reconnects after 5 s if it drops.
  2. Queue. Hashes enter a queue of 2 000. When full, the oldest is dropped. A worker fetches full transactions at 20 requests per second with eth_getTransactionByHash.
  3. Buffer. Fetched transactions go into a rolling buffer of 3 000. Swaps are identified by an allow-list of 20 routers and 25 function selectors.
  4. Match. For each new swap, find an earlier transaction from the same sender in the same pool key with higher gas, and a victim from a different sender with gas between the two, all inside 12 s.
server.js · detectRealSandwich (condensed)

victim    : other sender, gasPrice < front and > new tx
all three : within SANDWICH_WINDOW_MS = 12 000, same pool key
cooldown  : one detection per attacker per 12 s

The eviction defect

Bug found during evaluationWhen the buffer first exceeded 3 000 entries, the eviction loop read a field that did not exist on the entry, which threw a TypeError. Every later transaction raised an exception that the code caught and discarded, so Layer 1 silently stopped analysing. In a 60 000-transaction run this caused about 57 000 exceptions and a recall below 0.01. The fix is a one-word change in the comparison.

Limits

  • Private order flow (bundles) never appears as pending, so those attacks are invisible here.
  • The fetch cap lets through about a fifth of pending hashes on mainnet (see live results).
  • The pool key is router plus selector, not the actual pool, so two pools sharing both are treated as one.
  • Layer 1 produced no mainnet detection in 120 minutes. With no positive case, this is not evidence about the rule's accuracy.
Design

Layer 2: block reconstruction

The primary detector. It reads each mined block and reconstructs the sandwich from transaction order.

Algorithm

Layer 2 matching rule
input : block with m transactions in block order     output: D, at most 5 candidates
if m < 3: return []
S  = txs with a destination, destination not in the 18-token blacklist, calldata >= 100 bytes
group S by key (sender, destination); keep groups with 2+ members
for each group G, each ordered pair (a, b) in G with a before b:
    for each v in S between a and b:
        if sender(v) != sender(a) and destination(v) != destination(a):
            add (a, v, b); stop searching G
    if |D| == 5: return D

Why it works

Attackers usually send both legs from one address to a contract they control, so grouping by (sender, contract) finds the legs without decoding calldata. Requiring the victim to be on a different contract excludes bots that only call their own contract.

Filters

Calldata ≥ 100 bytes

Real swaps carry 100+ bytes. Plain token transfers carry about 68.

Token blacklist (18)

USDT, USDC, DAI, BUSD, USDP, FRAX, TUSD, WETH, WBTC, LINK, UNI, MATIC, SHIB, APE, BAT, SAND, CHZ, YFI.

Cap of 5 per block

Bounds work and flag volume. It limits recall in blocks above 400 transactions.

Limits

  • Attacks with legs from different senders, calldata shorter than 100 bytes, or a victim that uses the attacker's own contract are outside the rule.
  • The first swap-shaped transaction between the legs is taken as the victim. On the synthetic workload it is the injected victim in only about a third of detections (0.32–0.35). Whether an attack is reported is unaffected, but the reported victim is unreliable.
  • On mainnet the rule alone is about 7 % precise. See validation.
Design

Token-flow validation

A second stage that confirms or rejects each candidate from the transaction receipts.

Fetch receipts. One eth_getBlockReceipts call per block, used for all candidates in it.
Reverts. Reject if the front-run, victim or back-run reverted.
Net flows. From ERC-20 Transfer logs, compute each address's net balance change per token for each transaction.
Shared pool. Find a pool address and token whose net change has the same sign in the front-run and the victim's swap. Otherwise reject.
Unwind. The back-run must move that pool in the opposite direction by 0.8 to 1.25 times the front-run.
Profit. The attacker must end with more of the quote token than it started with.

Outcome on mainnet

Limits

  • Pool identity comes from the token holder, which cannot separate pools that share one holder (for example Uniswap v4's singleton). The one validated false positive was of this kind.
  • The profit test uses the quote token only and is not net of gas. Four validated candidates passed with a gross profit of six raw units.
  • It does not decode calldata, handle native-ether legs, or estimate the victim's loss.
Design

ReputationSlippage contract

Solidity 0.8.20, compiled with Hardhat. Deployed on Base Sepolia at 0xb6CD63eb…db82.

Behaviour

  • recordAttack(attacker) is owner only. It increments the attack count, sets the flag and emits AttackRecorded.
  • Reputation = staked amount × blocks since staking. A flagged address with c recorded attacks has it multiplied by (10 − c)/10, capped at 9 attacks.
  • Allowed slippage is a step function of reputation: 500, 200, 100, 10 or 1 basis points.
  • executeSwap checks an output against the allowed slippage and emits SwapExecuted.

Gas (local Hardhat node)

A first recordAttack for an address writes empty storage (70 922 gas); a repeat costs 33 922. The figures exclude the data fee that Base charges for posting calldata to Ethereum.

Limitations of the contractIt records an attacker but does not prevent a sandwich, and it matters only to applications that read it. It relies on one owner key, and a false positive cannot be undone. The tier thresholds are fixed numbers in wei × blocks, so for a stake of about one ether the reputation exceeds the top tier after one block and a reduction of at most 90 % does not move it down a tier. A flagged address that never stakes has zero reputation in any case. The thresholds need rescaling before the tiers separate realistic stakes.

On-chain bridge

  • flagAttacker() signs with the owner key and sends recordAttack(attacker) with a gas limit of 300 000, then waits for the receipt.
  • A repeat flag for the same attacker is throttled for 10 minutes.
  • A reverted transaction is reported and the process continues.
  • Known issue: concurrent flags from one account reuse a nonce and are lost (see chain results). Assign nonces explicitly or send one at a time.

Labelling protocol (mainnet)

There is no list of true attacks on mainnet. A candidate was labelled an attack if the victim's swap touched the same pool as the attacker's legs in the direction of the front-run, the back-run reversed the front-run, and the attacker's balance change was positive. All 25 validated candidates were labelled, with a systematic sample of 25 of the 342 rejected ones, presented in random order. 24 of 25 validated could be judged; one could not be decided from the transfers. The labels were assigned by the author without a second labeller.

Results

Detection accuracy

On the synthetic workload Layer 2 reaches precision ≈ 0.74 and recall ≈ 0.75. Both depend on the assumed mix and decoy rate, not on mainnet.

Block size

Precision stays between 0.725 and 0.746. Recall is 0.743–0.761 up to 400 transactions per block, then falls to 0.452 at 800 and 0.231 at 1 600. The cause is the cap of five detections per block: a block of 800 holds about 8 injected sandwiches, so recall is bounded by about 0.75 × 5/8 ≈ 0.47. This is a configuration limit, not a loss of detection ability. The experiment was not repeated with a higher cap.

Worker threads

Precision (0.737) and recall (0.748) are identical for 1 to 16 nodes. Sharding blocks over workers does not change the result.

Decoy sensitivity

Reading the decoy rateLayer 2 reports any (sender, contract) pair around another sender's swap, so a trading bot acting twice around an unrelated swap looks like an attack. With sandwiches at 1 % and 75 % found, about 0.75 true detections occur per 100 transactions, so each added decoy rate d (per 100 tx) lowers precision to 0.75/(0.75 + d). The measured values match. Real traffic has far more look-alikes than 0.25 %: the structural rule alone was only about 7 % precise on mainnet.

Layer 1 on the synthetic workload

Corrected Layer 1 has precision 1.00 and recall 0.11–0.13, because it recognises only router-based attacks (type B, 15 %) that also satisfy the gas ordering (80 %). The version first built has recall below 0.01. See Layer 1.

Results

Latency, throughput and scaling

The analysis is fast. On mainnet the delay is set by the network and the provider, and scaling over threads peaks at 2.5× on this machine.

Analysis time

Mean analysis time grows from 0.03 ms at 50 transactions per block to 1.47 ms at 1 600 (95th percentile 0.04 to 2.75 ms), close to proportional to block size. Layer 1 costs 76 µs per pending transaction at 50 tx/block and 224 µs at 1 600.

Throughput

These rates are for in-memory analysis of generated blocks. They exclude network and RPC cost and are far above the 24.8 tx/s that mainnet supplied on average in the live run (178 660 transactions in 7 200 s).

Scalability

Speed-up is 1.93 at two nodes and peaks at 2.52 at four, then falls to 2.39 at eight and 1.78 at 16. The processor has six physical cores and 12 hardware threads, so the plateau is consistent with competition for cores and shared resources. Memory bandwidth and scheduling were not examined, so the cause was not isolated. This is scaling on one machine, not across machines.

Results

On-chain recording: inclusion and gas

Gas is not the limit. Nonce handling is: concurrent submission from one account lost almost every transaction.

FindingWhen several detections were submitted at once from one account, each took the account's next nonce from the node before the others were mined. The node accepted the first and rejected the rest as replacements with too small a fee increase. Inclusion was 1/n for a burst of n. Explicit nonces gave inclusion 1.00 everywhere.

Burst size (one submitter)

Number of submitter nodes (batch of 20)

Sharding keeps total gas near 1.42 million whatever the number of nodes. Replication raises it to 2.10, 3.45 and 6.17 million for 2, 4 and 8 nodes because each node repeats the same writes. The growth is less than proportional since repeated writes to an address cost less than the first.

Confirmation time

The mean confirmation time was 1.6 to 2.1 s in every configuration (single repetitions 1.3 to 2.3 s), which reflects the 2 s block interval set for the local node, not the contract. Confirmation on Base Sepolia was not measured.

ScopeThe test is the worst case, with many detections at the same moment from one account. The backend throttles a repeat flag for the same attacker to once per ten minutes, so the loss appears only when several different attackers are flagged at about the same time. The flag path as built still cannot be relied on under bursts.

Candidates over time

Candidates accumulated steadily at about three per minute (96 after 30 min, 191 after 60, 277 after 90, 367 after 120).

Effect of validation

  • Of 25 validated, 24 could be judged: 23 were attacks and one was not.
  • One validated candidate could not be labelled because its net profit could not be decided from the transfers.
  • Of a systematic sample of 25 of the 342 rejected candidates, none was an attack (upper 95 % bound 0.133).
  • Weighting the two groups by size gives about 0.065 precision for the structural rule alone (interval 0.054–0.19). Validation raised the precision of reported detections from about 7 % to about 96 %.
  • The 25 validated detections came from 24 blocks and 11 attacker addresses; two addresses account for 14 of them.
Limits of this estimateThe sample is small and the intervals are wide. The author assigned the labels from the receipts, and the validator uses a related criterion, so the two are not independent. Recall cannot be measured on mainnet because no complete list of attacks exists: the results say how often an alarm was right, not how many attacks were missed. Only 25 of 342 rejected candidates were checked.

By block size

The candidate rate rises with block size from about 23 per 100 blocks for blocks up to 200 transactions to about 106 for 500–600. The last two bins hold only 5 and 3 blocks, so the fall in the final bin is noise. Larger blocks contain more look-alike activity, so the structural rule over-reports more in busy blocks.

Layer 1 intake

About 4 060 hashes arrived per minute against a fetch cap of 20 per second. About 1 066 fetches were attempted per minute and 813 returned a transaction (20 % of hashes received). The rest were dropped from the full queue (about 2 980 per minute) or returned nothing because the transaction had left the pool (about 24 % of attempts). The mean age of a hash at fetch was 0.58 s. Layer 1 saw about a fifth of the public mempool, which lowers its recall independently of its rule.

The 25 validated detections

Addresses are abbreviated. TP = attack, FP = not an attack, by the author's judgement from the receipts. The one FP was a Uniswap v4 trade in which attacker and victim used the same pool manager but different pairs.

Threats to validity

  • Construct. Synthetic precision and recall measure the detector against the author's own definition of an attack, not field performance.
  • Internal. Timings come from a laptop running other software. Three or five repetitions make the error bars approximate.
  • External. One two-hour window of mainnet traffic from one provider. Attack frequency and mix vary over time.
  • Label. Labels rest on a receipt criterion and the author's judgement; the validator uses a related criterion.

What the results do not support

They do not support claims about mainnet recall, about financial harm prevented, or about behaviour on Base Sepolia under load. They support three statements: validation is needed for the heuristic to be usable on live data; the detector's own computation is not the bottleneck; and the path from detection to an on-chain record needs careful transaction management.

Future work

  • A labelled set of independently verified sandwiches, to estimate recall.
  • Linking addresses to catch split-sender attacks.
  • A price-based profit test and an estimate of the victim's loss by replaying the swap on a forked state.
  • Setting the per-block cap and the 12 s window from data.
  • A multi-signature or quorum writer, and rescaled reputation thresholds.

FAQ and glossary

Is this real-time?

It is near-real-time, or block-time. Layer 2 analyses each block as it arrives and reported a candidate a median 0.52 s after the block header. It is soft real-time: delay depends on the provider and network and was measured, not bounded. Detection is after inclusion, so it cannot protect the victim of the attack it reports. Layer 1 is the only early-warning path and it saw about a fifth of the pending pool.

Does it prevent sandwich attacks?

No. It records attackers on-chain and lowers their reputation in a contract. Only applications that read that contract are affected.

How accurate is it?

On the synthetic workload precision is about 0.74 and recall about 0.75, but both are set by the assumed mix. On mainnet, 23 of the 24 judged validated candidates were genuine (0.96), labelled by the author. Mainnet recall is unknown.

Why did Layer 1 find nothing?

Many sandwiches are sent as private bundles that never appear in the public pool, and the fetch cap let through only about a fifth of pending hashes. With no positive case, the result does not show whether the rule works on live data.

Why is recall low for large blocks?

Layer 2 reports at most five detections per block. In 800-transaction blocks the synthetic workload holds about eight sandwiches, so the cap bounds recall near 0.47.
